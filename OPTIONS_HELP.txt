View options:
    --fullscreen
        Display the app in full screen. The default is to display in a window
        instead, except on Android which always uses full screen.

        The app's output will be scaled to fit your screen. This is independent
        of the internal resolution, so if the scale hack (see below) is not also
        in use, the result may be a bit blurry. An internal resolution larger
        than your screen's is possible, in which case the output is downscaled.

    --landscape-left
    --landscape-right
    --upside-down
        Changes the orientation the virtual device will have at startup.
        The default is portrait.

        --landscape-left means rotate 90° counterclockwise from portrait.
        --landscape-right means rotate 90° clockwise from portrait.
        --upside-down means rotate 180° from portrait (portrait upside-down).

        Usually apps that require landscape mode will tell touchHLE about this,
        and it will automatically rotate the window, but some apps neglect to
        do this. These options may be useful in that case.

    --scale-hack=...
        Set a scaling factor for the window. touchHLE will attempt to run the
        app with an increased internal resolution. This is a hack and there's
        no guarantee it will work correctly for all apps.

        The default is no scale hack, which is equivalent to a value of 1 (i.e.
        a scale of 1×).

        This is a natural number that is at least 1.

    --ui-scale=...
        Set a resolution multiplier for the user interface that touchHLE
        itself renders (the app picker and UIKit-based app UIs). Layer
        bitmaps (including text) are rasterized at N times their logical
        size and composited into a proportionally larger framebuffer, which
        makes them sharp on high-resolution displays. This is a hack and
        there's no guarantee it will work correctly for all apps.

        The default is a value of 2 (i.e. a scale of 2×).

        This is a natural number that is at least 1.

Device options:
    --device-family=...
        Specifies which device family should be emulated: iPhone or iPad.
        This only work if running app does support selected family
        (or the option will be ignored).

        If omitted, suitable device family would be deduced from application
        bundle itself, falling back to iPhone if needed.

        Accepted values are "auto" plus any of the specific device models
        below. The legacy names "iphone", "iphone5" and "ipad" are still
        accepted as aliases (mapping to iPhone 3GS, iPhone 5 and iPad 2).

        iPhone family (32-bit):
            iphone-2g  (iPhone1,1)   iphone-3g  (iPhone1,2)
            iphone-3gs (iPhone2,1)   iphone-4   (iPhone3,1)
            iphone-4s  (iPhone4,1)   iphone-5   (iPhone5,1)
            iphone-5c  (iPhone5,3)
        iPad family (32-bit):
            ipad-1  (iPad1,1)   ipad-2  (iPad2,1)   ipad-3  (iPad3,1)
            ipad-4  (iPad3,4)   ipad-5  (iPad6,11)
            ipad-mini   (iPad2,5)   ipad-mini-2 (iPad4,4)
            ipad-mini-3 (iPad4,7)
        iPod touch family (32-bit):
            ipod-touch   (iPod1,1)   ipod-touch-2 (iPod2,1)
            ipod-touch-3 (iPod3,1)   ipod-touch-4 (iPod4,1)
            ipod-touch-5 (iPod5,1)

        A model's hardware identifier (e.g. "iphone4,1") is also accepted.

        Use "auto" to let touchHLE inspect your host display's resolution,
        expose that resolution directly to the app, and still pick the device
        family whose bundled resources are the closest match. The chosen family
        is still validated against what the app bundle supports, so an
        unsupported guess is ignored just like a manual override.

    --screen-size=WxH
        Force the emulated screen to be exactly W by H points (e.g.
        --screen-size=320x693), exposed to the app at scale 1.0, instead of one
        of the fixed device profiles. This is the manual counterpart to
        "--device-family=auto": auto detects your host display automatically,
        while this lets you pin any resolution you like. Width and height may be
        separated by "x", "X" or ",". The order is normalised to portrait
        (smaller value becomes the width), and the initial orientation option
        still applies. A manual --screen-size= always wins over the resolution
        auto-detection.
    --ios-version=MAJOR.MINOR[.PATCH]
        Select the iOS version reported to the game. The default is "Latest",
        currently the highest compatibility version exposed by HyperHLE.


Game controller options:
    --deadzone=...
        Configures the size of the \"dead zone\" for analog stick inputs.

        The default value is 0.1, which means that 10% of the stick's range on
        the X and Y axes around the center position will be collapsed into a
        single point, so that movements in that range are ignored.

        This is a floating-point (decimal) number between 0 and 1.

    --disable-analog-stick-tilt-controls
        Disables mapping of analog stick input to simulated rotation of the
        device.

        By default, if touchHLE detects a game controller, its analog sticks
        will be used for simulated accelerometer tilt controls. When this
        happens, the real accelerometer (e.g. on an Android phone), if present,
        is ignored. By setting this option, the real accelerometer can be used
        even if a game controller is detected. This may be useful on a device
        that integrates both an accelerometer and a game controller, or if you
        do not want to disconnect your game controller.

        Note that touchHLE does not currently support accelerometers contained
        within game controllers.

    --x-tilt-range=...
    --y-tilt-range=...
        Set the simulated rotation range of the device axis mapped to the analog
        stick X or Y axis, or to the mouse cursor's X or Y position within the
        window (when the right mouse button is held).

        Positive X and Y are mapped to tilting the device rightward and forward
        respectively.

        By default, an analog stick's axis is mapped to a rotation range of 60°
        (30° in either direction). If you wanted a range of 90° on the X axis,
        you could use --x-tilt-range=90.

        For historical reasons, the device's X axis is mapped to the analog
        stick's Y axis and vice versa, as if the device is held in landscape.

        This is a floating-point (decimal) number of degrees, without a degree
        symbol. It may be negative.

    --x-tilt-offset=...
    --y-tilt-offset=...
        Offset the simulated angle of the device axis mapped to the analog stick
        X or Y axis, or to the mouse cursor's X or Y position within the window
        (when the right mouse button is held).

        Positive X and Y are mapped to tilting the device rightward and forward
        respectively.

        By default, the device is simulated as being level with the ground when
        the stick is in the center/neutral position. This option is intended for
        games that use a different angle relative to the ground as their neutral
        position. For example, if a game expects you to hold the device in a
        landscape orientation, with a 45° angle to the ground, you might use
        --y-tilt-offset=45.

        This is a floating-point (decimal) number of degrees, without a degree
        symbol. It may be negative.

    --button-to-touch=...
        Maps a button on a game controller to a point on the simulated touch
        screen of the device. Pressing the button will behave like touching that
        part of the screen.

        This is three parts separated by commas: the name of a button (DPadLeft,
        DPadUp, DPadRight, DPadDown, Start, LeftShoulder or Xbox-like
        A, B, X or Y), the X co-ordinate and the Y co-ordinate.
        The co-ordinates are floating-point (decimal) numbers. 0,0 is the
        top-left corner. The bottom-right corner is 320,480 if the app is in
        portrait, and 480,320 if the app is in landscape.

        For example, --button-to-touch=A,470,310 will make the A button simulate
        tapping in the bottom-right corner of the screen, for a landscape game.

        Except where specified in touchHLE_default_options.txt, this is not used
        by default. There is however a virtual cursor that is controlled by the
        right analog stick (tap/hold by pressing the stick or right shoulder
        button).

    --dpad-to-touch=...
        Maps a D-pad on a game controller to simulated finger movement within a
        region of the simulated touch screen of the device. This is useful for
        games where diagonals are used.

        This is four parts separated by commas: x,y,w,h. The co-ordinates
        are floating-point (decimal) numbers. 0,0 is the top-left corner. The
        bottom-right corner is 320,480 if the app is in portrait, and 480,320
        if the app is in landscape.

        For example, --dpad-to-touch=10,10,50,50 will simulate an 8-directional
        D-pad within a 50x50 pixel region starting at (10,10) on the screen.

        Note that this option takes precedence over any D-pad buttons defined
        with --button-to-touch.

        Except where specified in touchHLE_default_options.txt, this is not used
        by default. There is however a virtual cursor that is controlled by the
        right analog stick (tap/hold by pressing the stick or right shoulder
        button).

    --stick-to-touch=...
        Maps the left analog stick to simulated finger movement within a region
        of the simulated touch screen of the device. This is useful for games
        which use analog movement controls.

        This is four parts separated by commas: x,y,w,h. The co-ordinates
        are floating-point (decimal) numbers. 0,0 is the top-left corner. The
        bottom-right corner is 320,480 if the app is in portrait, and 480,320
        if the app is in landscape.

        For example, --stick-to-touch=10,10,100,100 will map the left analog
        stick to control a touch within a 100x100 pixel region starting at
        (10,10) on the screen.

        Except where specified in touchHLE_default_options.txt, this is not used
        by default. There is however a virtual cursor that is controlled by the
        right analog stick (tap/hold by pressing the stick or right shoulder
        button).

    --right-stick-to-touch=...
        Maps the right analog stick to simulated finger movement within a
        region of the simulated touch screen, analogous to --stick-to-touch
        but for the right stick. This is useful for dual-stick FPS games
        (e.g. Dead Trigger) where the left stick is movement and the right
        stick is camera/aim. When this option is set, the virtual cursor for
        the right stick is disabled while the stick is mapped.

        This is four parts separated by commas: x,y,w,h. See --stick-to-touch
        for coordinate details.

        For example, --right-stick-to-touch=370,210,90,90 will map the right
        stick to a 90x90 region at (370,210) for camera control in landscape.

        Except where specified in touchHLE_default_options.txt, this is not used
        by default.

    --stabilize-virtual-cursor=...
        Apply motion smoothing and a sticky radius to the virtual cursor
        (controlled by the right analog stick).

        Some apps are very sensitive to small finger movements and will always
        register an attempted "tap" as a scrolling gesture if the finger moves
        even very slightly. When combined with the low precision and shakiness
        of the virtual cursor, it can be difficult to use certain apps' menus.
        This option exists to compensate for this.

        The value is two floating-point (decimal) numbers separated by a comma.
        The first is the strength of the motion smoothing, and the second is a
        radius, in pixels, within which movement of the cursor will be ignored.
        To increase these values is to trade off responsiveness and precision
        respectively. Either number can be zero if desired. Note that the effect
        of the sticky radius is *not* shown on-screen!

        For example, --stabilize-virtual-cursor=0.1,10 will smooth out movements
        such that sharp movements take about half a second to complete, while
        movements within a 10px radius will be completely ignored.

Graphics driver options:
    --gles2-compat
        Enables touchHLE's experimental OpenGL ES 2.0 subset using the desktop
        OpenGL 2.1 compatibility backend. This is an app-specific option and
        is not a complete implementation of OpenGL ES 2.0.

    --gles1=...
        Force touchHLE to use a particular OpenGL ES 1.1 implementation.
        This may be useful for troubleshooting graphics driver issues.

        --gles1=gles1_on_gl2 will use touchHLE's GLES1-on-GL2 layer.
        --gles1=gles1_native will use native OpenGL ES 1.1.

        When this option isn't in use, touchHLE will try each in order and use
        the first one that works.

Debugging options:
    --disable-direct-memory-access
        Force dynarmic to always access guest memory via the memory access
        callbacks, rather than using the fast direct access path (page tables).

    --gdb=...
        Starts touchHLE in debugging mode, listening for GDB remote serial
        protocol connections over TCP on the specified host and port.

        You can then connect to touchHLE with GDB and make use of its features
        to inspect memory and registers, set up software breakpoints, and
        continue or step execution.

        The host and port should be separated by a colon. The host can be a
        host name or an IP address. IPv6 addresses should be enclosed in square
        brackets, e.g. --gdb=[::1]:9001 for IPv6 loopback device port 9001.

    --no-error-popup
        Disables the graphical error message box (outputs to terminal/log file
        only).

    --dump=...
        Dumps some information about app/emulator to dump file. Check
        src/options.rs:parse_dump_options for the currently available options.

    --dump-file=...
        Pick the file for information to be dumped to, relative to the user
        data directory. Defaults to {user directory}/DUMP.txt. Note that this
        file will get truncated (deleted) if it already exists!

Other options:
    --preferred-languages=...
        Specifies a list of preferred languages to be reported to the app.

        This should be one or more ISO 639 language codes (usually two letters)
        in order of preference, separated by commas. For example,
        --preferred-languages=de,ja,en means you would prefer German, or failing
        that Japanese, or failing that English.

        If this option is not specified, the list comes from your operating
        system's language settings.

        Whether and how this preference is respected, and whether any particular
        language is supported, is determined entirely by the app.

    --headless
        Run in headless mode. touchHLE will not create a window, so there will
        be no graphical output and no input. Only useful for command-line apps.
        Implies --no-error-popup.

    --args
        All arguments following this option will be passed to the app (via C's
        argc/argv) rather than processed by touchHLE. This option can't be used
        via touchHLE_options.txt or touchHLE_default_options.txt.

    --print-fps
        Logs the current framerate (FPS) to the console once per second.

    --fps-limit=...
        Modify or disable the framerate (FPS) limit.

        By default, touchHLE limits the framerate of an app to 60fps, because
        this is required for accurate emulation. Some apps can however run
        correctly at a higher framerate than normal.

        This is either 'off', to disable the framerate limit, or otherwise
        a floating-point (decimal) number of frames per second.

        Note that many apps have an internal timer that determines how often
        they present frames; increasing the limit will not increase their
        framerate, but may make it less consistent.

    --force-composition
        Forces presentation of renderbuffer as if no fullscreen EAGL layer is
        present, i.e. renderbuffer will go through the compositor.

        Enabling this option may solve some rendering issues, but implies
        a performance hit which is undesirable in most of the cases.

    --present-mode=...
        How a frame that an app rendered into a fullscreen EAGL layer is put
        on the screen. One of:

        'auto' (default): present on the GPU (the renderbuffer is copied to a
        texture and drawn into the window). If the first frames come out
        black while the renderbuffer clearly has content, HyperHLE assumes the
        host driver mishandles this path and switches to 'readback' for the
        rest of the session (a message is logged).

        'direct': always present on the GPU, never fall back.

        'readback': read the frame back to system RAM with glReadPixels()
        and push it through the compositor, like older versions did on
        Android. This is much slower (a full GPU pipeline stall and two
        full-frame copies per frame), but it never touches the app's GL state,
        which makes it a useful workaround for buggy vendor OpenGL ES 1.1
        drivers.

        The environment variable TOUCHHLE_PRESENT_MODE accepts the same
        values; the option takes precedence over it.

    --present-finish
        Insert a glFinish() before the presented renderbuffer is copied to the
        window. Only useful for host drivers that fail to order that copy after
        the app's draws (symptom: stale or partially drawn frames). It costs a
        GPU pipeline stall per frame, so it is off by default. Can also be
        enabled with TOUCHHLE_PRESENT_FINISH=1; --no-present-finish turns it
        off again.

    --vsync=...
        Whether presenting a frame waits for the display's vertical refresh.
        One of:

        'auto' (default): on Android, off — HyperHLE paces frames itself (see
        --fps-limit) and the Android compositor is synchronised to the display
        anyway, so a blocking swap can only stall the emulator (a frame that
        takes slightly longer than one refresh then costs two, i.e. 60 FPS
        becomes 30 FPS). On other systems the driver's default is left alone.

        'on': every swap waits for the next refresh (swap interval 1).

        'off': swaps never wait (swap interval 0).

        The environment variable TOUCHHLE_VSYNC accepts the same values; the
        option takes precedence over it. --vsync and --no-vsync are shorthands
        for 'on' and 'off'.

    --gl-driver=...
        (Android only.) Which host OpenGL ES driver to use. One of:

        'auto' (default): apps whose executable only imports OpenGL ES 2.0
        shader entry points use the vendor's native driver. For apps that may
        use ES 1.1 (and the app picker), bundled ANGLE is selected only when
        Android exposes an Adreno KGSL GPU; other or unrecognized GPUs use the
        system driver instead. This avoids assuming that the bundled ANGLE's
        Vulkan backend is supported on every device. The log explains the
        choice.

        'angle': always use bundled ANGLE when available, regardless of the
        detected GPU. Use this to override the automatic safety check.

        'native': always use the vendor's native driver, even for ES 1.1 apps.

        The environment variable TOUCHHLE_GL_DRIVER accepts the same values;
        the option takes precedence over it.

    --no-perf-hints
        (Android only.) Don't raise the emulator thread's scheduling priority
        and don't report its per-frame CPU time to the system's performance
        hint manager (ADPF, Android 13+). By default both are done so that the
        CPU governor keeps the core clocked for the emulated workload instead
        of for the idle time between frames, which otherwise tends to make a
        game that could run at 60 FPS settle at 30. Can also be disabled with
        TOUCHHLE_PERF_HINTS=0; --perf-hints turns it back on.

    --prefer-gles2-context
        Force EAGL initWithAPI: to create an OpenGL ES 2.0 context even when
        the app requested an OpenGL ES 1.1 context.

        Some apps (e.g. Lego Ninjago Spinjitzu Scavenger Hunt) ask EAGL for an
        ES 1.1 context but actually drive rendering with shader entry points
        such as glUseProgram and glCreateShader. Without this flag, on real
        ES drivers (e.g. Adreno / Mali on Android) those calls fall through
        to the GLES 1.1-only stubs and the app renders an empty (black)
        frame even though its render loop is alive.

        Apps that legitimately rely on the ES 1.1 fixed-function pipeline
        (glMatrixMode, glColor4f, glEnableClientState, glVertexPointer, …)
        should NOT enable this flag, because real ES 2.0 has no fixed-function
        pipeline.

    --allow-network-access
        Allow apps running in touchHLE to access the Internet and the local network.

    --ignore-gl-errors
        Ignore host OpenGL errors as queried by glGetError function.
        This only affects return value of glGetError as seen by the guest
        and nothing else. Should be enabled only for apps which really
        need this behaviour.

    --trace-gl-errors
        For diagnostic builds. After every guest GL call dispatched through
        the GLES wrapper, also log the host driver's glGetError() value when
        non-zero. The log line includes the name of the offending entry
        point so that constant 0x500 (GL_INVALID_ENUM) / 0x501
        (GL_INVALID_VALUE) noise can be traced back to a specific call.
        This option exists for debugging black-screen / wrong-render bugs
        and adds a glGetError() round-trip per call, so it should not be
        left on for normal use.

    --fix-texture-min-filter
        Workaround for apps that rely on the default ES 1.1
        GL_TEXTURE_MIN_FILTER (GL_NEAREST_MIPMAP_LINEAR) being usable
        on a level-0-only texture. With this flag, after every
        glTexImage2D(level=0) call HyperHLE issues an extra
        glTexParameteri(GL_TEXTURE_MIN_FILTER, GL_LINEAR) so that
        strict drivers (notably Qualcomm Adreno's native ES 1.1 path)
        don't sample the texture as opaque black just because no
        mipmaps were uploaded. The guest's own glTexParameteri calls
        still override this. Apps that legitimately upload mipmaps
        should NOT enable this flag.

        On Android builds this workaround is enabled by default, because
        Android hosts essentially always run Mali / Adreno / similar
        strict drivers. On desktop hosts it stays off so pixel output is
        unchanged for the common case.

    --no-fix-texture-min-filter
        Explicitly disable the fix_texture_min_filter workaround described
        above. Useful on Android (where it is on by default) for the rare
        iOS title that legitimately relies on mipmap minification and
        would visibly lose quality under the forced GL_LINEAR.

    --zero-stack-after-guest-to-host-call=<bytes>
        After a guest-to-host call returns, zero out the given number of
        bytes immediately below the current stack pointer (i.e. the unused
        scratch region of the guest's full-descending stack).
        This option exists because a guest-to-host call leaves that region
        untouched, whereas a real call on iOS could leave it in a "dirty"
        state. This can make a difference for apps that store data on the
        stack and branch based on the stack's content. There is normally
        no reason to enable this option. The number of bytes must be
        chosen carefully on a per-app basis.

    --corrupt-game
        Enable the RTCV-style "game corruption" engine. This is ENABLED BY
        DEFAULT. At a configurable cadence the emulator overwrites random
        bytes of the running game's live memory with random values,
        producing the glitchy, "broken game" behaviour the Real-Time
        Corruptor (RTCV) is known for: corrupted graphics, audio, physics,
        and entertaining crashes. Only memory the guest has actually
        allocated is targeted, so the game keeps running (and glitching)
        instead of instantly crashing. This is implemented natively in Rust
        and therefore works on every platform HyperHLE runs on, including
        Android. Use --no-corrupt-game to disable it.

    --no-corrupt-game
        Disable the game corruption engine (it is on by default).

    --corrupt-interval=<frames>
        How many main-loop iterations to wait between corruption bursts.
        Lower is more aggressive. Default: 30. Implies --corrupt-game.

    --corrupt-intensity=<count>
        How many random bytes to corrupt per burst. Higher is more
        destructive. Default: 8. Implies --corrupt-game.

    --corrupt-seed=<number>
        Seed for the corruption PRNG. A given seed reproduces the same
        corruption stream, mirroring RTCV's reproducible-via-seed
        behaviour. Default: a fixed built-in seed. Implies --corrupt-game.

    --corrupt-max-offset=<bytes>
        Restrict corruption to the first <bytes> of each allocation, which
        tends to concentrate hits on object headers / hot fields. By
        default the whole of each allocation is eligible. Implies
        --corrupt-game.
